# 视觉目标与完成度校验

用于新场景的效果图设计确认，以及制作过程和交付前的视觉对照。沿用项目已有设计和验收记录；小任务可在交付说明中记录，不要求建立新的表格体系。

## 1. 先形成可确认的视觉目标

新场景或重大视觉方向变化时，在精细建模、批量资产制作之前：

1. 读取玩法/用途、实际镜头、目标设备、参考图及已确认限制。提取必须存在的对象、空间关系、视觉重点、风格与性能约束；不要只列物件名称。
2. 使用当前可用的 ImageGen 工具实际生成效果图，并遵循相应 `imagegen` 技能。风格未定时做少量有明确区别的方案；已定时只做与本轮决策有关的镜头。生成图应接近玩家实际视角，不能只靠电影式远景表达目标。
3. 实际查看并筛掉结构矛盾、无法交互或偏离要求的图；展示可审阅的图稿，说明推荐方向、必须保留的关系和仅作氛围参考的部分。请用户确认所选版本或指出修改。没有回复不视为确认；等待期间可进行不依赖视觉决定的工具检查、测量和可逆灰模验证。
4. 将确认的图片路径/版本及关键视觉条件保留在现有记录中。材料、轮廓、光照和构图应有可观察描述，而不是只写“高级”“精致”。新图取代旧目标时注明替代范围，避免同时追逐矛盾版本。

已有明确批准的效果图直接复用；用户明确跳过、只要灰模或技术演示时不强行生图。纯讨论不自动启动生成或制作。ImageGen 不可用时说明缺口，提出使用现有参考或灰模的替代方案，不把提示词当作完成的效果图。

概念图不保证几何和物理可实现。严格多视角一致性、尺寸或空间关系需要共享灰模验证，可将灰模渲染作为图像参考再定美术目标。目标图中的不可能结构应在扩展制作前解决，不能直接照抄或偷偷改掉。多视角组织按需使用已有 `game-scene-visual-exploration`，不复制一套图像探索流程。

效果图确认后，AI 按 [动效识别与检查](motion-review.md) 主动推导该场景的动态意图与静止边界；不要求用户提供完整动效清单。动效以时间和触发条件验收，不能只沿用静态目标图。

## 2. 固定三份比较依据

- **已确认目标**：判断是否满足视觉意图；标明参考用途和必须保留的条件。
- **上一版实际画面**：判断本轮是否改善、是否损坏已认可内容；新场景没有上一版时标记不适用，不伪造基线。
- **本版实际画面**：来自当前真实模型或游戏运行，标明资源/代码版本、镜头和运行环境。生成图不能充当实景。

将相关画面并排展示或制作对应图组，保留可打开的原图。尽量匹配机位、视角范围、画幅、时间和游戏状态；没有相机参数的概念图按地标与轮廓近似匹配，并注明不能严格像素对齐。自由视角要补关键侧面、接近过程和区域过渡，不能只挑最有利镜头。

灯光等本来就是修改目标时，不要求它保持不变，但其余条件应尽量一致。像素差异、覆盖率或图像相似度可以帮助定位变化，不能单独证明美术好坏或完成度。

## 3. 五个维度分别判断

| 维度 | 检查对象 | 典型证据 |
| --- | --- | --- |
| 内容完整 | 本阶段必须出现的主体、区域、道具、功能；占位物是否按约定替换 | 需求与实际对象/入口对应，缺项列表 |
| 空间与构图 | 大轮廓、尺度、相邻关系、通路、疏密、遮挡、视觉中心、前中后景 | 同视角整体图、必要的侧面或行走检查 |
| 美术完成度 | 形体接合、材质一致性、纹理尺度、受光与接触、近景细节、整体风格 | 实际整体图与重点局部，不只看单体资产 |
| 动态与交互 | 动作触发、循环/转换、中断、接触、反馈与玩家可读性 | 正常速度实播和真实输入流程 |
| 运行还原 | 目标引擎/设备中的材质、光照、透明、动画、画面与性能 | 目标运行画面及相关测量；离线任务检查最终编码输出 |

只评本轮适用项。灰模不按成品材质验收，静态资产不硬加玩法；但不能把明确要求的缺项改成“不适用”。每项使用：

- **PASS**：已有对应证据，满足本轮已确认要求。
- **PARTIAL**：已实现，但存在明确差距。
- **FAIL**：关键内容、视觉关系或行为不满足要求。
- **BLOCKED**：必要工具、设备或证据缺失，无法完成验证；注明“未验证”及具体原因。

不要用平均分掩盖关键失败，也不凭感觉报“完成 90%”。仅对有明确分母的离散项目报数量，例如“要求的 6 个入口中 5 个已验证”；它不等于整体视觉质量百分比。关键项由需求、玩家主流程和视觉目标确定，不能事后降级以取得通过。

## 4. 差距转成可执行修正

用简短记录串起：**位置/证据 → 与目标的差异 → 原因假设 → 本轮修改 → 复查方式**。

例如：入口主建筑被树冠遮挡，与目标的清晰轮廓不符；先验证树冠体量和位置，而不是给建筑加细节。修改后同机位复查，再查侧面是否出现空洞。

先解决影响整体的大问题，再修细节。模型组合失衡先查镜头、尺度和疏密；源渲染好而运行画面差先查导出、材质、曝光和阴影；静帧好而操作差则查镜头运动、动作和反馈。原因不确定时做最小对照，不能把推测写成事实或同时更改过多变量。

需要探索改法时，可把本版实景交给 ImageGen 做定向改善稿，保留机位、主要几何、路径和物件关系。实际查看生成结果，分清可实施的美术调整、几何漂移和新增成本；生成约束不能保证图像真的遵守约束。把可行修改落实到真实场景后再渲染。改善稿标为“建议稿”；只有用户确认目标变化时才替换批准基线，不能悄悄降低或改变验收条件。

## 5. 制作中检查，交付前覆盖整体

| 节点 | 通过条件与下一步 |
| --- | --- |
| 灰模空间核对 | 必须的区域、尺度、主轮廓、通路及镜头成立；结构关键项未通过时先修，不全面精修 |
| 代表性场景 | 一个能覆盖主要视觉/技术风险的组合区域，包含实际资产、材质、粗略到最终所需灯光、动态及交互；实时任务尽早进入目标引擎。验证后再扩展同类内容，不选最容易做漂亮的角落掩盖风险 |
| 整体交付 | 检查玩家会看到和操作的关键区域、过渡及状态，复查一致性与遗漏；不能用一个漂亮局部代表全场完成 |

空间阶段就用基础灯光看明暗构图，不把所有光照问题留到模型完成后。已定稿的局部修改只回查受影响节点及明显关联区域，不机械重跑全流程。技术和视觉复查由智能体在授权范围内完成，不把每次内部检查都变成用户审批；需要新的视觉决定时才请求确认。

交付给出目标与实景对照、关键差距、各适用维度结论及证据入口。约定关键项通过且剩余问题符合本轮交付阶段时才称本阶段完成；未完成就明确报告局部成果和缺口，不用文件数量或构建成功替代。自动检查负责资源、运行和可测条件，审美结论必须来自实际查看与播放。
